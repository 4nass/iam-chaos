# ADR-0002: Use a provider-neutral canonical identity model

- Status: Accepted
- Date: 2026-08-19

## Context

Keycloak, SCIM, Okta, Microsoft Entra ID, and AWS Cognito use different field names, constraints, and lifecycle rules.

If the generator creates provider-specific objects too early, the test scenario becomes coupled to one product. The same identity and event should be usable with several targets.

SCIM and OIDC are also different standards. SCIM is mainly used for provisioning. OIDC describes authentication claims. The internal model must not confuse them.

## Decision

The engine will use a provider-neutral canonical identity model. Target adapters will map this model to provider-specific payloads.

The model will contain at least:

~~~text
id
external_id
username
raw_username
normalized_username
emails[]
name
active
lifecycle_state
tenant_id
groups[]
roles[]
credential_profile
metadata
~~~

The model will be validated with Pydantic.

## Important rules

### Usernames

The model stores three values:

- raw_username: the exact value generated by the scenario;
- normalized_username: the canonical normalized value;
- target_username: the value produced by a target-specific policy.

Normalization policy must be explicit. NFC normalization and case folding must not be silently applied by the generator.

### Emails

Email is an array, not a single string. Each email can contain:

~~~text
value
type
primary
~~~

Verification state is kept as an identity or provider extension because it is not a universal SCIM core attribute.

### Lifecycle

The model contains both:

- active: a boolean used by many provisioning systems;
- lifecycle_state: a richer internal state such as ACTIVE, DISABLED, DELETED, or PENDING.

### Groups and roles

Groups and roles use neutral identifiers. Provider-specific paths, role namespaces, and IDs are created by the target adapter.

### Credentials

The model stores a credential profile, not a password in reports:

~~~text
known_password
force_reset
expired
disabled
none
~~~

The real test password, when needed, is provided only to the execution driver.

### Metadata

Every identity contains provenance metadata:

~~~text
scenario_id
scenario_version
seed_hash
seed_index
logical_time_ms
applied_mutations[]
~~~

## Consequences

Positive consequences:

- Scenarios can be reused across IAM products.
- Target-specific rules remain in adapters and capability files.
- Unicode and normalization collisions can be tested precisely.
- The origin of every generated identity can be traced.

Costs:

- The model is richer than a flat CSV row.
- Exporters must map arrays, extensions, roles, and lifecycle fields.
- Some provider-specific fields cannot be represented without an extension mechanism.
